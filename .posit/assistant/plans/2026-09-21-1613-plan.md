# Move application data storage to Supabase Storage

## Objective

Replace the current Google Drive publication and download of the Shiny app data with Supabase Storage, following the pattern in `sgbstats/dreamleague`. The data-producing scripts will publish a validated serialized R bundle to the existing `prmutuals` bucket. The Shiny app will retrieve and validate that bundle at startup before constructing its runtime objects.

This plan treats “all data storage” as the data required to build and serve the mutuals app: the results, runner metadata, event summary data, and distance/reference data. It does not migrate one-off analysis caches or generated Home-and-Away research outputs, because they are neither consumed by the app nor part of its current Google Drive publication flow.

## Current state

- `R/prmutuals.R` builds `all_results`, `runners`, `parkruns`, `date`, `events_done`, `names_ids`, and `names_all`; it writes `data/all_results.RDa` and uploads it to Google Drive.
- `R/distance.R` builds `distance` and `parkruns_list`; it writes `parkrunmutuals/distances.RDa`.
- `parkrunmutuals/app.R` authenticates to Google Drive, downloads `all_results.RDa`, then loads that file and local `distances.RDa`.
- `R/home_and_away.R` uses the local `distances.RDa` as a standalone analysis input, but its outputs are not used by the app.
- The reference project stores a single R bundle in Supabase Storage, uses the Storage REST endpoint directly through `httr`, validates configuration and HTTP failures, verifies the upload by downloading/loading it, and loads the same bundle in the app.

## Implementation steps

1. **Add a reusable Supabase Storage helper**
   - Create `R/supabase-storage.R`, adapted to this project rather than copied verbatim.
   - Define `supabase_storage_config()` with `SUPABASE_URL` and `SUPABASE_API_KEY`; default its bucket to `prmutuals` and fail clearly for an empty key, non-HTTPS project URL, or invalid bucket name.
   - Implement safe object-path URL construction, authorization headers, HTTP status validation, upload with `x-upsert: true`, and download to a temporary/local destination.
   - Add bundle-specific validation functions that load into an isolated environment and require these objects: `all_results`, `runners`, `parkruns`, `date`, `events_done`, `names_ids`, `names_all`, `distance`, and `parkruns_list`.
   - Use a single stable object path, proposed as `parkrunmutuals/data.RDa`, so writes are idempotent and readers always obtain the current published dataset.

2. **Publish a single complete app-data bundle**
   - Update `R/prmutuals.R` to source the helper and assemble the results-related objects as it does today.
   - Replace its Google Drive authentication and `drive_update()` with a Supabase upload of a temporary bundle containing all objects needed by the app.
   - Preserve the existing 25/30-second parkrun throttling (which already exceeds the project-required 23 seconds).
   - Download and validate the just-uploaded object before considering publication successful; abort with a useful error if upload or verification fails.
   - Keep local intermediate/raw caches only where needed to avoid re-fetching parkrun data during a build. Do not make Google Drive a fallback or a second publisher.

3. **Make distance/reference data part of the published bundle**
   - Refactor `R/distance.R` into a callable builder that returns `distance` and `parkruns_list`, rather than only saving a separate `distances.RDa` artifact.
   - Have the data publication workflow invoke that builder and include both objects in `data.RDa`.
   - Retire `parkrunmutuals/distances.RDa` as an app runtime dependency. The script may retain an optional local artifact only if it is useful for manual research, but app publishing must not depend on it.

4. **Load the bundle from Supabase in the Shiny app**
   - Add `parkrunmutuals/supabase-storage.R` (or include the shared helper in the deployment file) so the deployed app has its own runtime helper.
   - In `parkrunmutuals/app.R`, remove the Google OAuth setup, Drive authentication, Drive file ID, and download call.
   - Download the Supabase bundle to a `tempfile()`, validate it before assigning values, then assign the required objects to the app environment and continue using the existing UI/server logic unchanged.
   - Ensure the temporary bundle is removed with `on.exit()` and produce actionable startup errors for missing secrets, object not found, failed authorization, malformed bundle, or missing required objects.
   - Do not add a local or Google Drive fallback unless specifically requested; this keeps Supabase the single source of truth.

5. **Update related consumers and deployment configuration**
   - Update `R/home_and_away.R` to use the same bundle loader for `parkruns_list`, removing its direct reliance on `parkrunmutuals/distances.RDa`. Its own cache and analysis-output migration is explicitly out of scope for this change.
   - Update `parkrunmutuals/.posit/publish/parkrunmutuals-KQIK.toml` to include the helper file in the deployment bundle.
   - Confirm `httr` is recorded among deployment dependencies; add it only if Connect Cloud dependency discovery does not include it.
   - Keep secrets out of source control. Document that deployment must provide `SUPABASE_API_KEY`; `SUPABASE_URL` will use the same project URL as Dreamleague unless explicitly configured otherwise.

6. **Validation and tests**
   - Add focused tests for configuration validation, object-path construction, required-object validation, and a mocked upload/download round trip. Add a project test runner if none exists.
   - Run a production-like local publication using the existing environment variables, confirm that the `prmutuals/parkrunmutuals/data.RDa` object is overwritten successfully, then start the app and confirm it loads entirely from Supabase.
   - Compare the loaded bundle’s required object names, row counts, and key column classes against the pre-migration local artifacts to detect serialization/type regressions.
   - Confirm no Google Drive authentication or Google Drive package call remains in the app data path.

## Files expected to change

- `R/supabase-storage.R` — new shared publication/load helper.
- `R/prmutuals.R` — build, publish, and verify the Supabase bundle; remove Google Drive publication.
- `R/distance.R` — expose reusable reference-data builder and stop being the app’s separate file dependency.
- `R/home_and_away.R` — load `parkruns_list` from the bundle instead of `distances.RDa`.
- `parkrunmutuals/supabase-storage.R` — app-side helper, if deployment isolation warrants a copy.
- `parkrunmutuals/app.R` — load/validate the Supabase bundle; remove Google Drive startup code.
- `parkrunmutuals/.posit/publish/parkrunmutuals-KQIK.toml` — include the new app helper.
- New targeted test files and any minimal dependency metadata needed for reproducible checks.

## Deliberate exclusions

- Existing raw result CSVs, Home-and-Away RDS checkpoints, Home-and-Away CSV/RDS outputs, Google Sheets scripts, and historical/experimental scripts will remain local for now. They are separate workflows and migrating them would require a separate object naming, retention, and resumability design.
- No Supabase database tables are proposed. The requested Dreamleague-equivalent design uses Supabase **Storage**, with one validated serialized bundle as the application data contract.
